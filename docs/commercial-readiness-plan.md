# FluxFeed 商用化就绪改造方案

## 1. 文档目标

本文基于当前仓库的真实代码、部署配置、测试和压测结果，整理 FluxFeed 从“生产级架构原型”演进为“可面向真实用户运营的商业系统”仍需完成的工作。

当前判断：FluxFeed 的 Feed 技术主干已经具备较好的工程基础，但安全、内容治理、生产运维、质量保障和合规闭环仍不完整。现阶段更适合定义为 **可部署的生产级原型**，不建议未经整改直接公开商用。

本文默认目标是公开运营的 UGC 短视频产品。如果最终只作为企业内部 Feed 基础设施使用，可以降低内容审核和用户协议相关工作的优先级，但安全、可靠性、交付和数据治理要求仍然保留。

## 3. P0：公开上线前的阻断项

P0 的完成标准不是“已有设计”，而是代码、配置、测试和生产环境均已实际生效。

### 3.1 修复上传与静态文件安全风险

#### 当前问题

- `kind=file` 允许上传任意扩展名，并跳过 MIME 白名单。
- 上传文件由 API 通过 `/uploads` 直接公开。
- Web 将 `/uploads` 反向代理到同源 API。
- Web 将 JWT 保存到 `localStorage`。
- 上述组合可能形成同源存储型 XSS，并导致令牌泄露。
- 单次请求最大允许 1 GiB，缺少用户容量、文件数和转码并发配额。

#### 改造要求

1. 删除通用 `file` 上传类型，只保留明确业务类型。
2. 对扩展名、MIME、文件签名和解码结果同时校验。
3. 图片解码后重新编码，视频完成转码后才允许发布。
4. 上传内容迁移至对象存储，并使用独立静态资源域名。
5. 增加 `Content-Disposition`、`X-Content-Type-Options: nosniff` 和严格 CSP。
6. 增加单用户容量、上传频率、文件数、转码并发和失败任务清理策略。
7. 评估将登录态迁移到 `HttpOnly + Secure + SameSite` Cookie。

#### 验收标准

- 无法上传或直接访问 HTML、SVG、脚本等主动内容。
- 上传文件不能与 Web 应用共享可读取登录态的同源环境。
- 文件伪造、超限、截断、异常编解码和并发上传均有自动化测试。
- 对象存储中的孤儿文件可以自动回收。

### 3.2 统一保护内部接口

#### 当前问题

部分 `/internal` 接口没有内部 Token 鉴权：

- `POST /internal/recommendation-candidates`
- `POST /internal/exposure-decisions`
- `POST /internal/exposures`

#### 改造要求

1. 在 `/internal` 路由组统一挂载鉴权中间件，禁止逐接口选择性配置。
2. 生产环境优先使用集群网络隔离与服务身份认证，静态 Token 仅作为过渡方案。
3. 内部接口加入请求来源、调用方、操作结果和 Trace ID 审计。
4. 为未授权、错误 Token 和空 Token 增加路由级测试。

#### 验收标准

- 所有内部接口在公网入口不可访问。
- 缺失或错误身份凭证统一返回 401/403。
- 新增内部路由时默认继承保护，不需要开发者重复挂载中间件。

### 3.3 移除固定密钥和默认账号

**状态：代码与仓库配置改造已完成；外部 Secret Manager 接入和既有凭据轮换需在目标环境执行。**

#### 当前问题

配置和部署文件中存在固定 JWT 密钥、内部 Token、MySQL root 密码、RabbitMQ 默认账号和 Grafana 默认账号。

#### 改造要求

1. 所有秘密通过环境变量、Kubernetes Secret 或 Secret Manager 注入。
2. 启动时拒绝占位值、空值、默认密码和低强度 JWT 密钥。
3. 应用使用最小权限数据库账号，禁止使用 root。
4. Redis、Kafka、RabbitMQ 和可观测性后台启用认证；跨主机通信启用 TLS。
5. 建立密钥轮换和应急吊销流程。
6. 如果仓库中的凭据曾用于外部环境，立即轮换并清理 Git 历史。

#### 验收标准

- [x] Git 仓库和镜像配置不再包含生产秘密。
- [x] `FLUXFEED_ENV=production` 时会拒绝弱凭据、root/guest 账号和未启用 TLS 的依赖。
- [x] 密钥通过环境变量或 Kubernetes Secret 注入，轮换不需要重新构建镜像。
- [x] CI 包含 Gitleaks 秘密扫描。
- [ ] 在目标生产环境接入 Secret Manager，并完成首次密钥轮换与应急演练。

实现与操作说明见 [secrets-management.md](secrets-management.md)。

### 3.4 建立内容审核与处置闭环

**状态：首版闭环已实现。** 已落地视频/评论待审状态、规则机审与可信回调、人工审核、举报与申诉、用户屏蔽和封禁、内容下架/恢复、管理员 RBAC、操作审计、媒体访问控制及 Feed 可见性过滤。当前机审为可替换规则实现；搜索、对象存储和 CDN 接入仍按本方案范围留待后续基础设施阶段。

#### 当前问题

视频创建后直接进入 `Published`，没有审核状态流转。前端出现“审核中”展示，但后端不存在对应审核流程。

#### 最小可商用状态机

```text
Draft
  → Processing
  → PendingReview
  → Published
  → Offline / Deleted

PendingReview
  → Rejected
  → AppealPending
  → Published / Rejected
```

#### 改造要求

1. 视频、封面、标题和评论进入审核链路。
2. 未审核通过的内容不得进入 Feed、缓存和 Fanout。
3. 支持机审结果、人工复审、拒绝原因和申诉。
4. 支持举报、屏蔽、封禁、下架和恢复。
5. 建立运营管理后台和管理员 RBAC。
6. 所有管理操作记录操作人、原因、前后状态和时间。

#### 验收标准

- 普通用户无法绕过审核直接发布内容。
- 内容下架后能从详情、Feed、缓存、搜索结果和 CDN 中及时失效。
- 管理员操作可追溯，申诉结果可回查。

### 3.5 明确版权与法律基础

#### 当前问题

README 声明项目基于 GCFeed 二次开发，但仓库没有实际的 `LICENSE`、`NOTICE` 或第三方素材授权清单。

#### 改造要求

1. 核实原项目许可证是否允许商业使用、修改和再分发。
2. 补齐 `LICENSE`、`NOTICE` 和版权声明。
3. 核对图片、字体、图标、前端素材和测试视频的授权。
4. 建立用户协议、隐私政策和版权投诉流程。
5. 正式上线前由具备资质的法律人员复核目标市场要求。

#### 验收标准

- 所有代码和素材都能说明来源与授权范围。
- 用户在注册或关键数据处理前能查看并确认适用协议。
- 版权投诉、内容下架和申诉有明确处理流程。

## 4. P1：稳定运营与收费所需能力

### 4.1 完善账号与权限体系

- 增加账号、密码和昵称的长度及格式限制。
- 增加邮箱或手机号验证、找回密码和修改密码。
- 引入 Refresh Token、设备会话列表、单设备退出和全部设备退出。
- 校验用户状态，封禁用户不得继续登录或使用旧 Token。
- 高风险操作从数据库读取实时权限，避免长期信任 JWT 中的旧角色。
- 增加登录失败限制、撞库检测、异常设备识别和安全审计。
- 管理后台使用明确的 RBAC，不依赖单个 `admin` 字符串判断全部权限。

验收重点：封禁、改密、退出全部设备和角色撤销可以在明确时限内生效。

### 4.2 建设正式媒体处理链路

```text
客户端
  → 获取预签名凭证
  → 直接上传对象存储
  → 转码、截图、内容审核
  → 写入媒体元数据
  → 审核通过
  → CDN 分发并进入 Feed
```

需要支持：

- 分片和断点续传；
- 视频清晰度梯度、封面和缩略图；
- 转码任务重试、超时和死信；
- 防盗链、签名 URL 和 CDN 缓存失效；
- 原始文件、转码文件和失败任务的生命周期管理；
- 删除视频时数据库、缓存、对象存储和 CDN 的最终一致性。

### 4.3 改造数据库迁移流程

当前 API 和 Worker 都会在启动时执行 GORM `AutoMigrate`。生产环境需要：

1. 使用版本化迁移文件。
2. 迁移作为独立部署任务执行。
3. 发布前校验向前、向后兼容性。
4. 大表变更提供在线变更方案和回滚步骤。
5. 应用账号不持有修改表结构权限。

### 4.4 完善事件一致性和多 Worker 安全

#### Outbox

- 为待发送事件增加原子领取、租约或数据库锁。
- 防止多个 Worker 同时发布同一事件。
- 支持失败事件重放、人工查看和批量处理。
- 定期归档已发布事件，避免 Outbox 表无限增长。

#### Consumer

- 将幂等记录与业务更新放入同一数据库事务。
- 对无法事务化的外部副作用使用业务幂等键。
- 明确各事件的至少一次投递语义及可接受的重复行为。
- 建立 Schema 版本与兼容性策略。

#### 验收标准

- API、Worker 各扩为两个以上副本后，不出现重复计数或重复消息。
- Worker 在处理成功但提交 Offset 前崩溃，恢复后业务结果仍正确。
- DLQ 事件可以安全重放。

### 4.5 建立生产级部署基线

最低要求：

- API、Worker、Web 多副本；
- Ingress、TLS、证书续期和可信代理配置；
- CPU/内存 requests 与 limits；
- HPA、PDB 和滚动更新策略；
- 非 root、只读根文件系统、最小 Linux Capability；
- NetworkPolicy 和服务间访问白名单；
- 镜像使用不可变版本或 digest，禁止生产使用 `latest`；
- API 分离 `/livez` 与 `/readyz`；
- Worker 增加存活、就绪和积压健康检查；
- MySQL、Redis、Kafka 使用托管服务或生产级高可用方案。

### 4.6 建立备份与灾难恢复

需要明确并验证：

- MySQL 全量与增量备份；
- 对象存储版本和删除保护；
- Redis、Kafka 是否属于可重建数据，以及重建路径；
- RPO、RTO 和责任人；
- 至少季度执行一次恢复演练；
- 备份加密、访问控制、保留期限和跨区域策略。

验收标准不能只检查“备份任务成功”，必须实际恢复出一套可启动环境并验证核心数据。

### 4.7 从监控升级到可响应的可观测体系

已有 Prometheus、Grafana、Tempo，应优先补齐：

- API 可用率、P95/P99、5xx 和超时告警；
- Kafka lag、DLQ 和消费失败率；
- Outbox pending、failed 和最老事件年龄；
- MySQL 连接池、慢查询、复制延迟和磁盘容量；
- Redis 命中率、内存、淘汰和错误率；
- 上传、转码和审核失败率；
- SLO、错误预算和分级告警；
- Runbook、值班机制和事故复盘模板；
- 日志脱敏、保存周期和访问权限。

### 4.8 建立 CI/CD 与质量门禁

建议 CI 最小流水线：

```text
gofmt check
  → go vet
  → go test
  → go test -race
  → frontend build/lint/test
  → dependency and secret scan
  → container build and scan
  → integration test
  → publish immutable image
```

测试优先覆盖资金和安全以外的核心业务风险：

1. 账号登录、状态和权限；
2. 上传边界和恶意文件；
3. 视频状态机和审核；
4. 点赞、关注、评论的并发一致性；
5. Outbox、重复消费和故障恢复；
6. Feed 缓存失效和降级；
7. 内部路由鉴权；
8. 数据库迁移兼容性。

第一阶段可把关键业务覆盖率提升到约 60%，不机械追求全仓库 100%。

## 5. P2：商业产品与合规闭环

### 5.1 用户数据权利

- 隐私政策和处理目的说明；
- 用户授权与协议版本记录；
- 账号注销；
- 个人数据导出；
- 数据删除与备份删除策略；
- 数据保留期限；
- 第三方处理方和跨境传输清单；
- 推荐个性化关闭入口。

### 5.2 内容与社区治理

- 举报分类、证据、处理状态和通知；
- 用户屏蔽、评论删除和关键词治理；
- 封禁期限、处罚历史和申诉；
- 版权投诉和侵权内容处置；
- 未成年人保护；
- 推荐降权、强制下架和人工干预审计。

### 5.3 运营支持

- 客服工单和反馈处理；
- 公告、服务状态页和故障通知；
- 管理后台的数据修正与人工补偿；
- 用户增长、留存和内容供给指标；
- 容量成本、对象存储、CDN 和转码成本核算。

支付、订阅、广告或会员系统是否建设，应由商业模式决定，不作为“技术可商用”的默认前提。

## 6. 分阶段实施计划

### Phase 1：关闭安全与合规阻断项

目标：系统可以进入受控内测。

- 修复上传安全和同源资源风险；
- 统一保护 `/internal`；
- 秘密外置并增加启动校验；
- 建立最小内容审核、举报和下架流程；
- 明确 License、协议和隐私基础；
- 为以上能力增加自动化测试。

退出标准：安全审查无 P0 问题，未审核内容不能公开，生产环境无默认凭据。

### Phase 2：建立可靠生产环境

目标：可以承载小规模真实用户和持续发布。

- 对象存储、转码和 CDN；
- 版本化数据库迁移；
- CI/CD、镜像扫描、灰度和回滚；
- Outbox 多 Worker 安全和消费事务幂等；
- 多副本、资源限制、探针和网络隔离；
- 告警、备份恢复和 Runbook；
- 核心业务自动化测试。

退出标准：单实例故障不导致服务长时间不可用，发布可回滚，数据可从备份恢复。

### Phase 3：容量验证与正式运营

目标：形成有数据依据的容量和运营承诺。

- 执行 100 RPS × 15 分钟验收；
- 执行至少 50 RPS × 30～60 分钟稳定性测试；
- 注入 MySQL、Redis、Kafka、Worker 和网络故障；
- 验证扩缩容、重平衡、积压追赶和缓存重建；
- 验证账号注销、数据导出、投诉和申诉流程；
- 完成容量、成本、SLO 和应急责任人确认。

退出标准：性能、稳定性、安全、恢复和运营流程均有可重复的验收记录。
